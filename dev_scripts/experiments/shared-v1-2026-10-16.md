# Shared-backbone v1 pilot — 2026-10-16

## Protocol

- Statement initialization: **generic `Salesforce/codet5-base`**, not a PyLingual statement checkpoint. This keeps the same upstream initialization as ordinary PyLingual.
- One shared statement backbone and one shared segmentation backbone; only **3.14 and 3.15** adapters are retained in the evaluated family. This preserves PyLingual's two-task pipeline rather than pretending it is one neural network.
- Backbone data: scraper run `2026-07-02-14`, Python **3.6–3.14**, **64 training + 16 validation files per version**. File sampling and optimizer batches are version-balanced; per-file row sampling prevents very large files dominating. Python **3.15 is absent from both backbone training and tokenizer fitting**.
- There are 101 distinct source hashes in backbone training and 23 in validation; versions share many sources. These are not 576 unrelated training programs.
- Adapter data: 64 training + 16 validation files for each of **3.14 and 3.15**. 3.15 is out-of-backbone-distribution, **not zero-shot** after adapter training. No remaining version adapters were trained for this final v1 family.
- Statement backbone: 6,000 updates. Segmentation backbone: 1,150 updates, warm-started from the Python 3.9 segmenter with the classifier reset and union opcode vocabulary. Segmentation therefore is **not** a generic-initialization ablation.
- LoRA rank 8, alpha 16, 600 updates per task/version, frozen backbone, attention query/value targets; no external PEFT dependency. Statement input/output limits are 512/128 tokens. Training ran over SSH on `pylingual-train`.
- File benchmark: 8 held-out `.pyc` files per target version from `pylingual_eval_dataset`, pinned at `c0226b218dbbd8b76511e69e4ff601cab3caeb71`, with a 30-second per-file deadline. Both versions use the same selected source identities. This is the actual v2 compiled-file benchmark, **not** the misleadingly similarly named Hugging Face component datasets.
- A pass means PyLingual's strict bytecode-equivalence verifier accepts the entire file. Compile failures, differences, and timeouts are failures. All configurations use the same files, interpreter builds, timeout, and pipeline. Compiler handling was corrected to tolerate successful prerelease-interpreter warnings and expose actual generated-source line numbers to error correction.

## Strict whole-file accuracy

| Configuration | Python 3.14 | Python 3.15 |
|---|---:|---:|
| Deployed version specialists | 3/8 (37.5%) | 0/8 (0.0%) |
| Shared translator, no LoRA; deployed segmenter | 0/8 (0.0%) | 0/8 (0.0%) |
| Shared translator + LoRA; deployed segmenter | 0/8 (0.0%) | 0/8 (0.0%) |
| Shared translator + segmenter, both with LoRA | 0/8 (0.0%) | 0/8 (0.0%) |

The deployed 3.14 reference passes three files; every shared configuration fails all eight. All configurations fail all eight 3.15 files, so this sample does **not** establish comparable 3.15 quality. The machine-readable companion records compile-error/difference/timeout counts. These are not pass rates conditional on compilation succeeding.

## Component checks, not whole-file accuracy

64 eligible held-out scraper examples per task/version, drawn from the separate validation split. These independently exercise each shared family; the file-level no-adapter condition above uses the deployed segmenter:

| Component | 3.14, no LoRA | 3.14, LoRA | 3.15, no LoRA | 3.15, LoRA |
|---|---:|---:|---:|---:|
| Statement exact match | 84.4% | 84.4% | 79.7% | 79.7% |
| Segmentation boundary F1 | 85.4% | 85.3% | 81.0% | 84.1% |

Statement exact counts are 54/64 for 3.14 and 51/64 for 3.15, both with and without LoRA. There is **no measured statement exact-match gain from LoRA** in this sample. The 3.15 segmentation adapter improves boundary F1 by 3.1 percentage points, but this has not translated into passing files. Component accuracy must not be presented as decompilation success.

## Model-weight memory

For both target versions resident, float32 parameters only:

| Architecture | Weight footprint |
|---|---:|
| Two deployed specialist pairs | 2.470 GiB |
| Shared backbones + two adapter pairs | 1.246 GiB |

This is **49.6% less model-weight memory (1.98× smaller)** for two versions. A statement adapter is 884,736 parameters and a segmentation adapter is 294,912 parameters: **4.5 MiB per version** together at float32. Backbones total 332,194,563 parameters. These are weight counts, **not measured peak inference VRAM**; activations, allocator behavior, generation caches, and duplicated model instances are excluded. Savings would grow when replacing more version specialists, but only the two adapters above were trained.

## Interpretation and limitations

- The architecture and adapter switching work; this tiny model run is **not an accuracy win** or a production replacement.
- Generic CodeT5 initialization makes the statement experiment compatible with the intended baseline starting point. However, deployed specialist checkpoints use different training corpora and compute. Their comparison is a useful reference, **not a fully matched training ablation**. A defensible performance claim needs same-data/same-budget per-version CodeT5 controls.
- Eight files per version is a smoke test, not a reliable benchmark estimate. The training corpus is deliberately tiny; per-statement errors compound across a full file. More balanced source files are the next priority before increasing model size or drawing transfer conclusions.
- Source-hash overlap checks are available, not proof that semantic near-duplicates are absent across independent corpora. Validation examples also omit overlength rows.
- 3.15 is held out of the backbone, but its adapter is supervised on 3.15. Its component results indicate some cross-version transfer; they do not demonstrate zero-shot or whole-file generalization.
- The segmentation warm start is an explicit separate variable; do not attribute its behavior solely to universal-backbone training.
